# 003｜专家团协作体验：交付、质量与成长计数

实验日期：2026-09-21；复核与归档日期：2026-09-22（北京时间）。

## 结论

通过桌面界面使用了产品战略、工程保障、内容创作、智数分析四个专家团。前三组先由主理人直接回答，随后追加针对具体问题的成员复核；第四组从起始需求就要求成员独立核对。界面出现创建团队、成员任务与完成状态，证明此次确实触发了协作流程。

但这不是专家能力排名，也未证明团队优于单个专家。没有统一测试题、随机对照或精确成本明细。9 月 22 日刷新成长中心后，“召唤 3 次专家团”仍显示 2/3，100 积分和 5 能量尚未领取。不能把完成对话等同于活动达标。

## 实验过程与结果

派发时核对主理人模型为 Hy4 preview。界面当时标注限时免费，权限显示允许完全访问；子成员模型和独立费用未逐一核实，因此不宣称整轮零成本。所有需求限定为小范围文字任务，不部署、不发布、不读取私人文件。

| 专家团 | 实际任务 | 观察结果 | 质量边界 |

| 内容创作 | 解释专家角色与独立训练模型的区别，再由文案成员校正 | 首轮约 15 秒；协作轮约 3 分 21 秒 | 首轮表述过于绝对；复核加入微调可能性，但“多数/少数”的比例判断仍没有调查依据 |

这些耗时是 WorkBuddy 界面显示的单轮处理时长，不含 Codex 操作、等待平台计数等全部时间。首轮和协作轮的需求不同，不能据此计算公平的速度或质量提升比例。

### 可独立核对的模拟数据

以下数据为人为构造，仅演示计算，不是真实专家表现：

```text
普通模式：[3, 4, 3, 5, 2]
专家模式：[4, 4, 4, 4, 3]
配对差值：[1, 0, 1, -1, 1]
```

均分分别为 3.4 和 3.8，平均差值 0.4，专家 3 胜、1 平、1 负。以上算术已核对。

智数团队部分过程性总结声称“剔除任一观测结论即翻转”，这一说法不成立：依次去掉一个差值后，平均差仍分别为 0.25、0.5、0.25、0.75、0.25，方向均为正。因此，成员与主理人都声称复核一致，仍不等于全部解释正确。模拟数据本身也不能用来断言真实能力差异。

## 方法上的收获

1. 区分角色指令、主理人直接回答与真正的成员协作；名字叫“团队”不代表每轮都启动多个成员。
2. 复核应围绕具体缺陷：本次对总量为零的矛盾和绝对化表述有帮助。
3. 协作增加了调度、等待、汇总和偶发重试成本；小任务不一定值得启动团队。
4. 对交付质量、平台活动计数和奖励到账分别验收，避免混报。
5. 精确 token 和积分成本缺失；此前口头给出的 token 量级只是粗估，不作为测量结果收录。

## 下一轮建议：先测试单个专家是否带来可用收益

先做一个本地小工具的同题对照，再决定是否扩大样本。建议以离线学习目标追踪器为任务，比较普通模式与“程枢”；均使用相同模型、权限、独立新对话及完全相同的需求，不给某组额外提示。

预先写好 6 条验收条件：正常创建、进度计算、空名称、负数及非数字、总量零及完成量越界、刷新后数据保持。规定修改失败时旧数据保持不变；存储规则和取整规则写进共同需求。

每组先各生成一次，独立运行测试并匿名评分，记录首次通过数、修正轮次、实际操作耗时、界面可获取的费用和越界操作。若值得继续，再在同一领域扩展到至少 3 种小任务并重复运行。小样本只用于发现问题，不发布“最强专家”结论。

优先顺序：

1. 同模型、同题的普通模式与单专家对照。
2. 对照显示价值后，再比较单专家与专家团的增益是否值得等待和费用。
3. 专家流程迁入 Codex：检查许可及依赖后再适配，当前仍未安装。

本节是后续实验设计，尚未派发或运行。活动计数异常另行保留，不靠持续重复派任务来代替诊断。
