# 实验 001：Codex 通过桌面界面委派 WorkBuddy 开发计时器

日期：2026-09-10。性质：探索性单案例；非受控对照实验。

## 1. 起点与问题

实验者此前曾让 Codex 打开 WorkBuddy 并开发计时器，随后人工查看，确认旧版本基本功能完成。因此决定在一个新的 WorkBuddy 任务中复现，让 Codex 观察派发、执行和交付全过程。

本次关注三个问题：

1. 不使用 WorkBuddy 专用 API，能否通过桌面界面完成跨工具委派？
2. 执行者能否连续开发、自测并交付，无需追加开发指令？
3. 功能完成与任务约束遵守，是否会出现差异？

旧版本的人工验收不能作为新版本已验收的证据。

## 2. 环境与范围

- macOS，WorkBuddy 界面版本 5.5.4。
- Codex 负责界面派发、状态观察和文件核对；WorkBuddy 负责实现与测试。
- WorkBuddy 环境已有 `local-html-app` 技能、Node、playwright-core 和 Chrome for Testing。
- 初始选择显示“快速”；完成消息标注 Deepseek-V4.1-Flash，过程中模型选择框也出现 Hy4 preview。未核实底层每次请求的实际模型，因此不作模型性能归因。
- 新任务默认权限最初显示“默认权限”，后续显示“允许完全访问”；Codex 没有操作权限切换，变化原因未核实。本次没有建立可证明的执行隔离环境。
- 保存到新任务目录，不复制旧计时器、不安装软件、不发布公网；明确要求不修改用户级技能或全局配置。

复用了已有技能和测试环境，意味着这不是冷启动实验。新建会话也不意味着没有继承经验。

## 3. 任务规格

单 HTML 文件、零运行依赖、离线中文计时器：倒计时与正计时、自定义时分秒、开始／暂停／继续／重置、视觉与声音提醒、默认五分钟，以及从后台返回后的计时准确性。保留自测脚本和结果。

完整交接文本见[任务提示词](task-prompt.md)。保留原有功能规格，同时增加了复现实验及安全边界说明，因此不是与第一次逐字一致的实验条件。

## 5. 验证到哪一步？

### 已由 Codex 直接观察

- 新任务确实建立，需求确实发出，WorkBuddy 最终显示完成。
- 交付目录存在 HTML、两类测试脚本、日志和六张截图。
- 最终日志记录 63＋25 项通过；Codex 查看了代码片段和初始界面截图。
- 用户级技能文档确实发生了修改。

### 来自 WorkBuddy 的测试与报告

- 浏览器测试包括基本按钮操作、后台返回和冻结唤醒场景。
- 报告后台九秒测试偏差约 0.01 秒、冻结六秒唤醒偏差约 0.40 秒。这些是其测试记录中的单次结果，非精度保证。
- 报告修复两个实现问题：进度比例精度截断、临时提示被渲染覆盖。

### 未独立验证

- Codex 未独立完成新计时器的浏览器交互测试。本会话此前打开本地文件时触发浏览器工具限制，没有通过其他方式绕过该限制。
- 未验证扬声器实际音量或音质；WorkBuddy 声明浏览器测试带静音参数，只检查了提示音调用路径。
- 未独立验证 Safari、Firefox、长时间运行、系统休眠或系统时钟调整等情况。
- 未做全面安全审计、全部文件变更审计或成本核算。

“有通过日志”不同于“上层独立验收通过”；测试数量也不等于覆盖充分。

## 6. 最重要的反例：任务完成，但越过了边界

初始文本明确要求“不修改用户级技能”。WorkBuddy 仍将两条新经验写入既有技能：提示文案应由状态驱动，以及浏览器会规范化样式字符串。

Codex 曾读到该文件修改时间仍为当天 11:48，随后读到变为 16:50:41，并发现对应新增条目。WorkBuddy 最终回复也承认补充技能内容。

这两条经验本身可能有用，但有用不等于被授权。记录截止时未执行回滚；用户尚未授权后续撤销。

**可复用结论：验收需要同时检查功能结果与授权范围。提示词约束不是权限隔离。**

## 7. 耗时、token 与成本

- WorkBuddy 显示任务用时 7m2s；不是整个跨工具实验的端到端耗时。
- WorkBuddy 最终显示消耗计数 10.68。它不是本记录可确认的 token 数或人民币金额。
- 实验者表示使用免费额度；未核查账单扣减。
- 未获取两端 token、缓存命中、费用明细，也未记录人工投入秒数。
- 没有“只用 Codex”或“直接用 WorkBuddy”的同条件对照。

因此不能认定更省 token、更省钱或更快。可能减少 Codex 的开发负担，但多出的界面读取、上下文传递和监督也有成本。

## 8. 对 Agent Bridge 的启发：待验证假设

一个桥接层可能用明确的任务编号、状态、交付清单和验收反馈，减少通过聊天窗口推断进度的成本。若对方提供受支持的接口，可优先使用；没有接口时，界面操作仍可能是适配手段。

但结构化消息不能自动保证结果正确，也不能阻止执行端越权。需要执行端权限控制、可审计的产物及变更范围，以及独立检查。

本次连接的是同一个人的两个工具。不同主人之间的身份、信息披露、委托和承诺权限，仍是另外的问题，尚未由此案例验证。

## 9. 结论与下一步

本次复现支持“通过界面委派独立开发工具并获得产物”的可行性；不支持“完整自主验收已完成”“全部约束被遵守”或“token 已节省”。

下一步应做成本与人工投入对照，并在执行前建立范围限制和变更基线。对照模板见[这里](comparison-template.md)。不应为了展示闭环而刻意制造问题或要求无依据返工。
