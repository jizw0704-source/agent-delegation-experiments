# 后续对照实验记录表

目标：比较直接使用开发工具与跨工具委派，是否减少人的投入，而非只比较生成速度。

## 实验方式

- A：只用 Codex。
- B：直接用 WorkBuddy。
- C：Codex 委派 WorkBuddy。

采用难度相当的任务与相同验收标准；记录已有技能、环境和模型，交替实验顺序并重复多次。避免后跑的一组直接复用前一组产物。记录失败、超时和人工接管，不只选择成功案例。

## 每次填写

| 项目 | 记录 |
| --- | --- |
| 日期／任务编号／实验方式 | 待填 |
| 工具版本／模型／已有技能 | 待填；不确定则明确标注 |
| 任务要求与验收标准 | 待填 |
| 允许写入范围与禁止动作 | 待填 |
| 执行前变更基线与隔离方式 | 待填 |
| 人的实际投入分钟数 | 写需求、补充信息、检查、处理故障分别记录 |
| 人的介入次数及原因 | 待填 |
| 委派者追加指令次数及原因 | 待填 |
| 总耗时 | 从需求发送到验收结束，不只记开发时间 |
| 首次交付是否合格 | 按统一清单填写，不能只引用完成声明 |
| 执行者自测与独立验收 | 分开记录 |
| 返工次数／发现者 | 待填 |
| 意外修改与权限越界 | 待填 |
| 两端 token／额度／实际费用 | 分开记录，无法取得则标为未知 |
| 最终状态 | 合格／部分完成／失败／人工接管 |

## 判断原则

1. 先比较交付质量与权限遵守，再比较时间和成本。
2. 免费额度不等于没有计算消耗；平台积分不能直接相加或换算成 token。
3. 独立检查不能只问执行者“是否通过”，应核验实际产物。
4. 界面操作可行，不代表一定比直接接口可靠；桥接层本身也需要测试。
5. 记录单次结果与范围，不将小样本外推成普遍结论。
